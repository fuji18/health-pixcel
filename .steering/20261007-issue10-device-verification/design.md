# 設計: MVP の実機検証とリリース確認(#10)

<!-- status: ready -->

実機での作業手順と判定基準。コマンドは Windows の **Git Bash**(`scripts/*.sh` が `sh` のため)で、リポジトリのルートから実行する前提。パッケージ名は `io.github.fuji18.healthpixcel`。

## 0. 準備

1. `docs/development-guidelines.md`「実機確認の準備」の 1〜2 を済ませる(Health Sync → ヘルスコネクトの同期、データの存在確認)
2. main の最新を取り込み、リリース APK を作って入れる。**計測・突き合わせはすべてリリースビルドで行う**(デバッグビルドは JIT で遅く、計測値が意味を持たない)

   ```bash
   git pull
   flutter clean && flutter pub get
   flutter build apk --release
   flutter install --release
   ```

3. 既にアプリが入っていて権限を許可済みなら、初回起動(C1)の確認のために一度アンインストールしてから入れ直す(`adb uninstall io.github.fuji18.healthpixcel`)

## 2. HUAWEIヘルスケアとの突き合わせ(C2)

- 対象: アプリに表示された 7 日分(今日を含む)。**今日の歩数は途中値で同期遅れがあるため、比較は前日以前の 6 日を必須、今日は参考**とする
- 同じ時刻帯に両アプリを見比べる(Health Sync の同期直後が望ましい。同期を手動で走らせてから比べる)
- 書き写す値(日ごと): HUAWEI の歩数 / アプリの歩数 / HUAWEI の睡眠時間・就寝・起床 / アプリの睡眠時間・就寝・起床。**生の値はリポジトリ外のメモ(手元の表計算など)に書き、results.md には差分・差率・合否だけを書く**(リポジトリが public のため。§8)
- 判定:
  - **歩数**: 一致(差 0)を合格とする。差がある日は原因を推定して書く(同期遅れ・Health Sync が書き込む時刻の丸め・複数の書き込み元など)。原因を書けない差は不具合候補として司令塔に戻す
  - **睡眠の就寝・起床**: 分単位で一致を合格とする。帰属日が起床日になっていること(日付をまたぐ睡眠で確認)
  - **睡眠時間**: 日ごとの差率 = (アプリ − HUAWEI) / HUAWEI。**6 日の差率の絶対値の平均**を results.md に書く
- HUAWEI が「深い/浅い/レム/覚醒」の内訳を出している場合は、覚醒時間も書き写す(§6 の判断材料)

## 3. 時間の計測(C8・C9)

計測は画面録画で行う(アプリにタイマーを足さない)。

```bash
# 開発者向けオプション → 「タップを表示」をオンにしておく(タップの瞬間が録画に映る)
adb shell am force-stop io.github.fuji18.healthpixcel   # コールドスタートにする
adb shell screenrecord --time-limit 15 /sdcard/cold1.mp4
# 録画中にランチャーのアイコンをタップ → 7 日分が出るまで待つ
adb pull /sdcard/cold1.mp4
```

- **起動時間** = アイコンのタップが映ったフレーム → 歩数・睡眠の両セクションに値(または「記録なし」)が出揃ったフレーム。動画プレイヤーのコマ送り(VLC なら `E` キー)で読む
- **再読み込み時間** = 下に引く指を離したフレーム → インジケータが消えて値が出揃ったフレーム
- 各 3 回。録画は毎回 force-stop からやり直す(再読み込みは続けて 3 回でよい)
- 補助値として `adb shell am start -W -n io.github.fuji18.healthpixcel/.MainActivity` の `TotalTime`(最初のフレームまで)も 1 回書いておく。基準の判定には使わない
- 録画ファイルには健康データが映るため、**リポジトリに入れない**(数値だけ results.md に書く)

## 4. リリース権限の検査(C5)

```bash
bash scripts/check-release-permissions.sh; echo "exit=$?"
```

加えて Android Studio の Build > Analyze APK で `build/app/outputs/flutter-apk/app-release.apk` → `AndroidManifest.xml` を開き、`android.permission.INTERNET` が無いことを目視する。`uses-permission` の一覧を results.md に書き写す。

## 5. logcat の確認(C7)

```bash
adb logcat -c
adb logcat --pid=$(adb shell pidof io.github.fuji18.healthpixcel) > logcat-app.txt   # アプリ起動後に実行
```

- アプリを起動してから上を実行し、表示 → 下に引いて再読み込み ×2 → C3 の権限変更からの復帰 を行ってから Ctrl+C
- プロセス外(ヘルスコネクト本体)のログは対象外。プラグインの Kotlin 側は同じプロセスなので含まれる
- `logcat-app.txt` を開き、画面に出ている歩数(例: `8432` と `8,432` の両方)、就寝・起床時刻(`23:30` 等)、睡眠の分数・秒数・エポックミリ秒らしき 13 桁の数値を検索する。**1 件でもあれば行を results.md に貼らず**、「どのタグの行か」だけ書いて司令塔に戻す
- `logcat-app.txt` は確認後に削除する(リポジトリに入れない)

## 6. 睡眠時間の定義の結論(docs への反映。司令塔が行う)

判定規則(PRD「未確定事項」より):

| §2 の平均差率 | 結論 | docs の変更 |
| --- | --- | --- |
| 10% 以下 | **セッション全体(終了 − 開始)で確定** | PRD「未確定事項」の該当行を削除し、「共通の定義」の睡眠時間に「(#10 の突き合わせで確定。平均差 X%)」を添える。`functional-design.md` に同旨の記述があれば揃える |
| 10% 超 | 見直し案を出す(覚醒を除く等)。MVP の定義は変えない | PRD「未確定事項」の該当行に結果と見直し案を書き、実装変更は**別チケット**にする(睡眠ステージの取得は P2 の検証事項と重なるため) |

## 7. 不具合が見つかったとき

- **小さい**(1〜2 ファイル・設計判断なし・権限/依存に触れない)→ 司令塔が修正内容を本ファイル末尾の「追補」に書き、`implement-ticket` に渡す。修正後はリリース APK を作り直し、該当項目だけ再確認する
- **大きい**(設計判断が要る・マニフェスト/依存に触れる・複数層にまたがる)→ 別 Issue に切り出し、results.md には Issue 番号を書く。本チケットはその項目を「既知の不具合(#N)」として記録すれば完了扱いにできる(C5・C7 を除く。プライバシー要件の不合格は本チケットを止める)
